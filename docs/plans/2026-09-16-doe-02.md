# DOE 02 — how much of the noise floor is the judge?

> **For Claude:** REQUIRED SUB-SKILL: Use `executing-plans` to implement this plan task-by-task.
> On execution, copy this file to `docs/plans/2026-09-16-doe-02.md` and commit it.

**Goal:** Split the noise floor into judge and agent non-determinism, run the campaign, and
record what the judge-model lever actually is — which is not what the repo currently implies.

**Tech Stack:** Python 3.11, `uv`, `wrangler capture` / `wrangler score`, Vertex Gen AI
evaluation service.

---

## Context

Resolution is the binding constraint on every experiment here. Campaign 08 returned
**unresolved** because a control arm drifted **0.022** on the holdout; DOE 11 needs n=4 per
condition to detect 56% of an effect. The floor is attributed in CLAUDE.md to "judge and
agent non-determinism" and **those have never been separated**. If the judge dominates, the
fix is cheap and needs no agent calls; if the agent dominates, `num_runs` is the only lever
and every reduction costs a full inference pass.

### Four findings from planning that change the shape of this campaign

**1. The stated blocker is stale.** DOE 02 says *"Depends on: `wrangler capture` /
`wrangler score`"*. **Both exist and are wired**: `wrangler capture --engine-id --eval-data`,
and `wrangler score <capture> --repeat N` whose help text already says N>1 "measures judge
non-determinism directly". Arms 1 and 2 are runnable today.

**2. The per-case data already exists and is thrown away at the CLI.**
`evaluator.score_captured_repeated()` returns `summary["results"]` — the full `EvalResult`
list including `per_case`. `cli.py:score_cmd` prints mean/sd/min/max and, on the `--repeat`
path, **saves nothing**. The pre-registration requires a *per-case disagreement rate*, so
this is a persistence gap, not a measurement gap.

**3. The batch-eval judge is not `DEFAULT_JUDGE_MODEL`, and is not configurable.** This is
the important one and it is currently mis-stated by implication across the repo:

| | judge | set by us? |
| --- | --- | --- |
| GEPA optimize stage | `DEFAULT_JUDGE_MODEL` = `gemini-3.5-flash` | yes, chosen by A/B 2026-08-20 |
| **Batch eval** (`eval_before` / `eval_after`) | **the Vertex service default autorater** | **no — and not recorded** |

Every campaign number — campaign 06's noise floor, campaign 07/08's criterion and holdout
deltas, the five-arm finding — comes from the second one. Evidence:

- `evaluator.py:144-147` says outright: *"do not set judge_model to a bare model id …
  Leaving it unset uses the service default autorater."*
- The four metrics that carry the results are `types.RubricMetric.*(version="v1")`, which
  are `LazyLoadedPrebuiltMetric` — resolved server-side, exposing no `judge_model`.
- `client.evals.create_evaluation_run()` has **no** autorater or judge parameter.
- `vertexai.types` has **no** `AutoraterConfig`. It exists only in
  `vertexai.preview.evaluation` — the legacy surface CLAUDE.md forbids mixing with
  `agentplatform`, having been bitten twice on 2026-09-08.

**4. One untried path remains.** `types.LLMMetric` *does* expose `judge_model`,
`judge_model_sampling_count` (1–32) and `judge_model_system_instruction`. CLAUDE.md records
only that a **bare model id** is rejected. A **full resource name** has never been tried. If
it works, the judge is controllable for our custom `tool_use_quality` metric and nothing
else — which is still worth knowing, because `judge_model_sampling_count` is exactly the
"score more times" lever this campaign is meant to price.

### Practical precondition, already satisfied

Captures need a healthy engine and the prune kept two. Both verified **ALIVE** today:
`gepa-c08-new-r1` = `4023875557346246656` (health gate 1.0, 572 requests) and
`gepa-c08-new-r2` = `5389381038113816576`. Using an existing engine removes the deploy
lottery from the design entirely. **They age out of the traffic window around 2026-10-11**,
so this campaign should run before then or it inherits a deploy step.

Eval set: `examples/multi_model_agents/eval_data/eval_cases.yaml`, **64 cases** confirmed.

## Task 1: Persist per-case results from repeated scoring

**Files:** `wrangler/cli.py` (`score_cmd`), `wrangler/eval/evaluator.py`,
`tests/test_score_repeat_percase.py` (new)

**Step 1 — failing test.** A `--repeat N` run must persist per-case rows for all N passes,
and a disagreement summary must be computable from them. Assert against a fake scorer, not
the service.

**Step 2.** `score_captured_repeated` already returns `results`; have `score_cmd` save them
via the existing `save_eval_results` (used on the single-score path) with a pass index, and
print a **per-case disagreement rate** alongside the existing sd table.

Reuse `summarize_repeats()` rather than writing new aggregation; extend it if it cannot
express per-case.

**Step 3.** Disagreement rate must be defined in the code, not left to the reader: the
fraction of cases whose score is not identical across all N passes, reported per metric.
State it in the help text — a rate whose definition is implicit gets misread.

## Task 2: Probe whether the autorater can be pinned at all

**Files:** `scripts/probe_autorater_control.py` (new)

**Findings only.** Follow `scripts/probe_optimizer_models.py`: re-runnable, arguments not
constants, and a docstring saying what a wrong result means.

Answer three questions against the live service, cheaply:

1. Does `types.LLMMetric(judge_model=<full resource name>)` succeed where a bare id fails?
   Use the `_TOOL_USE_JUDGE_PROMPT` metric already in `evaluator.py:_tool_use_metric()`.
2. Does `judge_model_sampling_count` change the result, and is it accepted on this surface?
3. Do the predefined `RubricMetric` kwargs reach the server at all? `LazyLoadedPrebuiltMetric.__call__`
   accepts arbitrary kwargs into `metric_kwargs`, but CLAUDE.md records that the predefined
   handler **ignores** rubric prefills and `metric_spec_parameters`. Establish whether
   `judge_model` is ignored or rejected — those are different and the distinction decides
   whether pinning is merely undocumented or genuinely impossible.

**Whatever the answer, it is a finding worth writing down**, because it determines whether
"use a different judge" is a lever for the metrics that carry our results.

## Task 3: Run the campaign

**No optimize stage, no agent deploy, no `main` freeze.** After the captures there are **no
agent calls at all**, so the GEAP empty-stream defect cannot touch this campaign.

| arm | method | measures |
| --- | --- | --- |
| **1 judge alone** | 1 capture, `score --repeat 5` | judge only — responses byte-identical |
| **2 agent + judge** | 5 captures, each scored once | agent + judge; subtract arm 1 for agent |
| **3 judge model** | per Task 2's probe | whether the lever exists |
| **4 tool-use prompt** | one capture scored with `_TOOL_USE_JUDGE_PROMPT` and a JSON-hardened variant | the effect of the prompt change, per case |

Six captures × 64 cases against `4023875557346246656`. Arm 4 reuses arm 1's capture — a
prompt comparison is only valid against identical responses, which is the whole reason
`capture` exists.

Arm 4 settles a standing blocker: the tool-use judge sometimes returns unparseable JSON and,
through the `extra='forbid'` cascade, one malformed response costs that case **every** metric
(silent-failures #9). The objection has been that changing the prompt changes every score it
produces. Against identical responses that stops being an objection and becomes a number.

**Pre-registered, unchanged from the existing DOE 02 where it still applies:** 5 repeats ×
64 cases; report per-metric **sd** and per-case disagreement rate, not only means; report the
malformed-JSON rate as a count; **no arm is extended because it looks interesting.**

## Estimated time, by task

**Grounded where it can be.** The compute figures extrapolate from eight measured
campaign-08 eval stages, all 64 cases; the coding figures are judgement.

Measured per-run cost of **inference + scoring together**, 64 cases
(`elapsed / num_runs` from each stage artifact):

```
  c08-new-r1  eval_before 14.5   eval_after  7.7   min/run
  c08-new-r2  eval_before 13.2   eval_after  6.1
  c08-ctrl-a  eval_before 11.0   eval_after  8.6
  c08-ctrl-b  eval_before 13.4   eval_after  9.1
                       range 6.1 - 14.5, mean 10.5 min
```

| task | estimate | basis |
| --- | --- | --- |
| 1 · per-case persistence | **30–45 min** | small change to one CLI path plus a fake-scorer test; `summarize_repeats` already exists |
| 2 · autorater probe | **45–75 min** | a few cheap calls, but the API surface is the unknown — the analogous LiteLLM id form took three attempts to find |
| 3 · **run the campaign** | **1.5–3 h**, mostly waiting | see below |
| 4 · write-up + judge-record correction | **45–60 min** | four files; the correction needs care, not length |
| | **≈ 4–6 h total** | dominated by task 3's wall clock, which is unattended |

**Task 3's range is wide for a reason I cannot close in advance.** The campaign needs
**6 captures** (inference) and **12 scoring passes**, but the measured 10.5 min is inference
*and* scoring combined and **the split has never been measured**. The two bounds:

- if scoring dominates → 12 × ~10.5 = **~126 min**
- if inference dominates → 6 × ~10.5 = **~63 min**
- even split → ~31 + ~63 = **~95 min**

So **60–130 min of compute**, call it 1.5–3 h with overhead. **The first capture-and-score
pair measures the split**, which prices everything after it — so take that reading before
launching the remaining five captures rather than discovering the cost at the end.

No step blocks `main`, nothing is frozen, and the waiting is unattended.

## Risks

- **The engines age out ~2026-10-11.** After that this campaign inherits a health-gated
  deploy and its lottery. Run it before then.
- **One engine, one draw.** All captures come from a single engine, so "agent variance" here
  is *within-engine* non-determinism and excludes the deployment lottery that DOE 01 measured
  at 0–100% reach. That is the right scope for this question and the wrong scope for "how
  much does an arm vary" — say so in the write-up rather than letting the number travel.
- **Arm 3 may return "not possible".** That is a result, not a failure, and the plan is
  written so the campaign still completes without it.
- **Judge non-determinism may be temperature-dependent and the autorater's temperature is
  not ours.** If arm 1's sd is near zero, consider that the service may cache or pin
  decoding — check for identical scores across passes before concluding the judge is stable.
