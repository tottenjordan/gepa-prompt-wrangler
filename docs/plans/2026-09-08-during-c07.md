## Context

Campaign 07's validation arm is ~195 min in and healthy: health gate `rate=1.0` first draw, eval-before **64/64 coverage**, GEPA confirmed calling `claude-sonnet-5` (200 `rawPredict` calls). When it reaches SUCCEEDED the driver releases **six more arms** — four optimizing, two controls — over roughly 25–32 h.

### The one hard constraint

**Do not touch `pyproject.toml`, `uv.lock`, or `Dockerfile.pipeline`.** The image tag is
`md5` of exactly those three. Changing any of them moves the tag, and the next
`submit()` would reference an image that does not exist until someone rebuilds
it — turning a campaign release into a failed submission.

Everything below is deliberately outside those three files.

### Why Task 1 is time-boxed

`scripts/run_campaign.py:submit()` calls `deploy_pipeline()` **in process**, which
packages the project tree **fresh at submission time**. So code on disk when
batch 1 releases is the code those six arms run.

That is a real, closing window: a fix landed before the validation arm finishes
reaches all six remaining arms. Landed after, it reaches none of them.

## Task 1: The MCP toolset race — diagnose, and fix only if the cause is clear

**Files:** likely `examples/multi_model_agents/registry.py` and the session-refresh path in `wrangler/pipeline/components.py` · Test `tests/test_mcp_session_refresh.py` (new)

### What is known

Three occurrences in the running optimize stage, at 15:30, 15:56 and 16:46:

```
Agent sonnet_agent will run without the tools from toolset McpToolset,
which failed to load: Failed to get tools from MCP server:
```

Established by inspection, not assumed:

- **The cause is empty.** Nothing follows the final colon — the underlying
  exception carried no message.
- **These are `localhost`, not Cloud Run.** The optimize component starts local
  FastMCP servers on 8001–8003 (`components.py:525-539`) and overrides the
  `*_MCP_URL` vars. Cloud Run cold starts and network are therefore ruled out.
- **It recovers.** Each generation logs
  `closing 3 stale MCP session(s)... re-warmed 3/3 in 0.1s`.
- **Rate is ~3 in 30 generations (~10%).**
- **The known mitigation is already applied.** Both registries set
  `tool_list_cache_ttl_seconds` (`deploy.py:598`,
  `examples/multi_model_agents/registry.py:61`), so this is *not* simply the
  documented cache-TTL fix being absent.

That combination — localhost, empty exception, recovers next generation,
survives the TTL fix — points at a race between the per-generation session
refresh and a concurrent `get_tools()`, which is the shape of
`docs/notes/silent-failures.md` §1b.

### Why it matters

A tool-using agent evaluated with an empty toolset scores near zero on tool use.
Those candidates are scored into the objective GEPA is optimizing, so the search
is being pulled by ~10% corrupted evaluations. `eval_before` scored
`tool_use_quality_v1` at **0.969**, so the agent is not the problem.

**Step 1 — quantify before touching anything.** Re-count both phrasings and
divide by generations reached:

```bash
gcloud logging read 'resource.type="ml_job" AND resource.labels.job_id="2987665159033454592"
  AND jsonPayload.message:"will run without the tools"' \
  --project="$GCP_PROJECT_ID" --freshness=6h --limit=500 \
  --format="value(timestamp)" | wc -l
```

**Decision rule, fixed now so the data cannot talk you out of it:**

| observed | action |
| --- | --- |
| rate stays ≲10% of generations | log it, fix the race, **do not** restart the arm |
| rate climbs above ~25% | the objective is materially corrupted — stop the arm, fix, resubmit |
| failures cluster at one timestamp | not a race; investigate that event instead |

**Step 2 — confirm the mechanism before writing code.** Correlate each failure
timestamp against the surrounding `closing N stale MCP session(s)` /
`re-warmed N/N` lines. If a failure lands inside a refresh window, the race is
confirmed. **If it does not, stop and re-diagnose** — the rest of this task
assumes a cause that has not yet been proven.

**Step 3 — write the failing test.** Test the refresh/`get_tools` interleaving
directly, with a fake toolset; do not reach the network.

```python
async def test_get_tools_during_a_session_refresh_does_not_return_empty():
    """A refresh must not expose a window where the toolset looks empty.

    Three candidates in campaign 07 were scored against an agent with no tools
    because get_tools() landed mid-refresh. The agent scores 0.969 on tool use
    when its tools are present, so those evaluations were pure noise fed into
    the objective GEPA optimizes.
    """
```

**Step 4 — implement the smallest fix the evidence supports.** Most likely a
lock or a swap-after-warm so the old session stays serving until the new one is
ready. Resist rewriting the session manager.

**Step 5 — verify, then commit and open a PR.** Full suite, ruff, ty. Note in
the PR that the fix reaches batch 1 only if merged before the validation arm
finishes, and say what the observed rate was.

## Task 2: Dry-run the campaign-07 analysis path against real artifacts

**Files:** no source changes expected · possibly `tests/test_campaign_floor.py`

Campaign 07's shape is confirmed from the manifests: **four optimizing arms**
(`sonnet5`, `sonnet46`, `pro`, `lite`) and **two controls** (`ctrl-sonnet5`,
`ctrl-lite`), all `num_runs: 3`. Discovering an analysis gap after 25–32 h of
compute is the expensive way to find one.

**Step 1 — run the floor tool against campaign 06's real, finished artifacts.**
Those exist and are the closest available stand-in:

```bash
uv run wrangler floor <c06-run-id> <c06-run-id-2> --markdown
```

`wrangler floor` accepts multiple run ids, so the two-control shape is already
supported — confirm it *produces* a per-metric floor, not just that it runs.

**Step 2 — confirm the per-metric floor reaches the verdicts.**
`analyzer.classify_deltas` takes a per-metric mapping, and `reporter` has
`_is_control_arm`. Trace one delta end to end and check it is classified
against **its own metric's** floor, not the scalar. Campaign 06 measured a 3.4×
spread across metrics (0.017 hallucination to 0.058 safety); collapsing to the
loosest throws away most of the resolution.

**Step 3 — check the six-arm report shape.** Every previous campaign was
smaller. Confirm the reporter orders and groups six arms sensibly and does not
assume a single control.

**Step 4 — write a test for whatever is missing**, or record that nothing is.
"I checked and it was fine" is a legitimate outcome; say so rather than
inventing work.

## Risks

- **Task 1's cause is not yet proven.** Step 2 exists to kill the task if the
  failures do not correlate with refresh windows. Writing the fix first and
  finding the correlation afterwards would be backwards.
- **The window may close before the fix lands.** The validation arm could finish
  in ~3 h. If it does, batch 1 goes out on current code; that is acceptable —
  ~10% degradation is a caveat on the results, not a reason to block them. Do
  not rush a session-manager change to beat a clock.
- **Touching the MCP servers is riskier than it looks.** The deployed Cloud Run
  servers serve the *eval* stages of the running campaign. Task 1 should change
  the client/refresh path, not redeploy those services.
- **Re-measuring for Task 3 costs an engine.** Deploy it with
  `lifecycle: ephemeral`, and reap it in the same session.
