# DOE 02 — the holdout's noise floor is the judge, and safety's is not

**Date:** 2026-09-16
**Pre-registration:** [../doe/02-judge-variance.md](../doe/02-judge-variance.md)
**Engine:** `4023875557346246656` (`gepa-c08-new-r1`), health gate 1.0
**Eval set:** `examples/multi_model_agents/eval_data/eval_cases.yaml`, 64 cases
**Status:** all four arms complete

## Headline

Scoring **byte-identical responses** five times, the judge disagrees with itself on
**64 of 64 cases** for `instruction_following_v1` and on **0 of 64** for `safety_v1`.

Those are the two metrics campaigns 07 and 08 are built on. The one that carries the
replicated effect is the one the judge scores perfectly consistently; the one that made
campaign 08 *unresolved* is the one the judge never scores the same way twice.

## Arm 1 — judge alone (1 capture, scored 5×)

Responses identical across passes, verified by checksum before and after: scoring does not
mutate a capture, so this is judge non-determinism and nothing else.

| metric | mean | **sd** | **cases disagreeing** |
| --- | --- | --- | --- |
| `instruction_following_v1` | 0.775 | **0.024** | **64/64 — 100%** |
| `final_response_quality_v1` | 0.886 | 0.023 | 38/64 — 59.4% |
| `hallucination_v1` | 0.952 | 0.010 | 28/64 — 43.8% |
| `tool_use_quality_v1` | 0.978 | 0.010 | 14/64 — 21.9% |
| `safety_v1` | 1.000 | **0.000** | **0/64 — 0%** |

## Arm 2 — agent + judge (5 captures, each scored once)

| metric | total sd across captures |
| --- | --- |
| `final_response_quality_v1` | 0.0308 |
| `safety_v1` | 0.0219 |
| `instruction_following_v1` | 0.0122 |
| `hallucination_v1` | 0.0104 |
| `tool_use_quality_v1` | 0.0090 |

## The variance subtraction does not work at n=5, and that is itself a finding

The pre-registered plan was agent = √(total² − judge²). Applied literally it returns
**judge = 386% of total variance** for `instruction_following_v1` — an impossible number,
and the tell that the method has hit its resolution limit rather than found something.

Simulated: when the true sd is 0.020, an sd estimated from **n=5** has a 95% interval of
**[0.007, 0.033]**. Two independent n=5 estimates of the *same* underlying variance can
easily differ by more than 2×. So 0.024 (arm 1) versus 0.0122 (arm 2) is sampling noise,
and no subtraction of two such estimates means anything for the low-variance metrics.

**The per-case disagreement rates are the robust statistic**, and this is why the
pre-registration demanded them. They are proportions over **64 cases**, not standard
deviations over 5 passes. `safety_v1` scoring identically on 64/64 cases across 5 passes is
not an estimate with error bars — it is exact agreement, 320 observations. Likewise
`instruction_following_v1` differing on 64/64 is a count, not a fit.

**Recommendation for anyone repeating this: the sds need n ≫ 5. The rates do not.**

## What this says about campaigns 07 and 08

**Campaign 08's IF control floor was 0.022. The judge alone produces sd 0.024 on that
metric, disagreeing on every single case.** Within the precision available, essentially all
of the holdout's floor is the judge re-reading identical text differently — not the agent,
and not dropout.

That reframes the result directly:

- **Campaign 08 returned "unresolved" on a metric whose floor we can now attribute.** The
  bar it failed to clear is a judge-consistency artifact, and the fix is therefore *cheap* —
  more scoring passes over the same responses, which needs **no agent calls at all** — rather
  than more `num_runs`, which costs a full inference pass each.
- **The replicated safety effect is on the most stable metric available.** `safety_v1` has
  judge sd 0.000 and a 0.0064 control floor, against a measured +0.154/+0.131 effect. Its
  entire floor (total sd 0.0219) is agent-side. That the five-arm finding sits on this
  metric makes it *more* credible, not less.
- **The criterion/holdout asymmetry may be partly instrumental.** GEPA improves a metric its
  judge scores consistently and degrades one its judge cannot score twice the same way. That
  does not explain the effect away — −0.053 is still twice the judge sd — but any future
  design reading the holdout needs to price this in.

## Arm 3 — the judge CAN be pinned, for the custom metric only

Answered, after two failed attempts that were both my harness.

| variant | result |
| --- | --- |
| no judge pinned (as shipped) | scored **0.9762**, coverage 63/64 |
| `judge_model="gemini-3.5-flash"` (bare id) | **400 INVALID_ARGUMENT** — the documented rejection still holds |
| **`judge_model="projects/…/locations/global/publishers/google/models/gemini-3.5-flash"`** | **scored 1.0, coverage 64/64** |
| `judge_model_sampling_count=4` | scored 0.9754, coverage 61/64 |

**The full resource name works.** CLAUDE.md records only that a *bare* model id is rejected
and concludes "the default autorater works" — true, but the full-path form was never tried.
It is accepted, and it is **honoured rather than ignored**: pinning the judge changed both
the score (0.9762 → 1.0) and the coverage (63 → 64). `judge_model_sampling_count` is also
accepted.

**This applies to `types.LLMMetric` only.** The four predefined metrics that carry every
campaign result are `LazyLoadedPrebuiltMetric`, resolved server-side with no judge field, and
`create_evaluation_run()` has no autorater parameter. So the lever exists for
`tool_use_quality` and for nothing else — which is still worth having, because a pinned judge
is a reproducible one.

### Both failures were the harness, and the second one is instructive

The first attempt failed every variant **including its own no-config baseline**. Ruled out:
identical metric objects (`model_dump()` diff empty), identical environment, and the
`LazyLoadedPrebuiltMetric` class-level cache.

The actual cause was importing `from vertexai import types` instead of
`from agentplatform import types`. **The client isinstance-checks its own types**, so the two
packages' objects have identical fields and different classes — `model_dump()` shows no diff
while the call fails. That is precisely the trap CLAUDE.md documents from 2026-09-08, and
`tests/test_sdk_private_surface.py` caught it the moment the script was linted. I had spent
considerably longer than that guessing.

Incidental finding from the isolation work: **a lone predefined metric fails to resolve while
a lone custom metric succeeds** — metric-list composition matters in a way nothing documents.

## Arm 4 — the hardened prompt: better coverage, same aggregate, different per-case

Designed and measured. `_TOOL_USE_JUDGE_PROMPT_HARDENED` sits beside the original in `evaluator.py`. It was the
measurement variant here and was **promoted to the live prompt on 2026-09-17** once this
result held at five passes; the original is kept as the reproducible control.

**The criteria text is byte-identical** (verified programmatically); only the output contract
differs: `score` first so truncation keeps the number, the explanation capped to one sentence
with no quotes/newlines/backslashes, code fences and preamble explicitly forbidden, and one
concrete example of a valid response. If the rubric had moved too, a score change could not
be attributed to the format and the standing objection would be unanswerable rather than
measured.

Both prompts scored against **the same capture** — the only valid way to compare them.

| | original | hardened |
| --- | --- | --- |
| coverage | 63/64 | **64/64** |
| mean over all scored cases | 0.9492 | 0.9609 |
| mean over the 63 **shared** cases | 0.9492 | 0.9603 |

### Confirmed at 5 passes each, 2026-09-16

The single-pass coverage result was one observation, so both prompts were then scored **five
times each** against the same capture, metric-list composition held constant so only the
prompt differs:

| | original | hardened |
| --- | --- | --- |
| cases scored | 312/320 — **8 lost** | **320/320 — 0 lost** |
| per pass | 63, 63, 60, 62, 64 | **64, 64, 64, 64, 64** |
| mean | 0.9663 | 0.9719 |
| **sd of the mean** | 0.0100 | **0.0043** |
| range | 0.9531–0.9762 | 0.9688–0.9766 |
| per-case disagreement | 20.3% | 18.8% |
| pairwise disagreement | 9.4% | 7.5% |

**The case loss is gone, not reduced** — zero across 320 scorings, against the original's 8,
including one pass that lost four cases at once (60/64). And the hardened prompt is **2.3×
more stable run to run** (sd 0.0043 vs 0.0100), which was not a predicted effect: a judge
that never has to improvise its output format also varies less in what it scores.

The mean difference (+0.0056) is well inside the *original's own* sd of 0.0100, so there is
still no material aggregate shift — the earlier single-pass conclusion holds with more behind
it.

### Against the right baseline, not a naive one

14.3% of shared cases changed score. That number means nothing until compared with how much
the judge moves **on its own**, so both were computed pairwise from arm 1's five passes:

| | same prompt, pass-vs-pass (10 pairs) | original vs hardened |
| --- | --- | --- |
| per-case disagreement | 6.6%–10.0%, mean **8.9%** | **14.3%** |
| \|difference in mean\| | mean **0.0112**, max 0.0246 | **0.0111** |

Two different answers, and the distinction is the whole point:

- **The aggregate does not move.** 0.0111 is almost exactly the *median* shift between two
  passes of the identical prompt (0.0112) and less than half the max. At the level campaign
  results are reported, the hardened prompt changes nothing detectable.
- **Per-case, it does move things.** 14.3% is above the full same-prompt range (max 10.0%
  over 10 pairs), so the prompt genuinely re-scores some cases rather than merely re-rolling
  them. This is **one** pairwise observation against a distribution of ten, so it is
  suggestive rather than established.

### Reading, against this campaign's own decision table

DOE 02 offered two outcomes: *"changes scores materially → ship only as a dated re-baseline"*
and *"fixes the JSON without moving scores → ship it"*. The answer is **between them**, and
splitting it is more useful than forcing it into one:

**Ship it.** Aggregate scores are indistinguishable from same-prompt noise, case loss is
eliminated (0/320 against 8/320), and run-to-run variance halves. But **per-case tool-use
comparisons must not cross the boundary** — 14.3% of cases re-score, above the hardened
prompt's own 7.5% pairwise self-disagreement; aggregate comparisons may.

### The premise was weaker than documented

silent-failures #9 describes an `extra='forbid'` cascade where one malformed metric response
costs that case **every** metric. **That is no longer happening.** Across arm 1's five passes,
of 26 case-losses, **zero** cases lost one metric and another — the losses are fully
independent per metric:

| metric | cases lost / 320 | |
| --- | --- | --- |
| `tool_use_quality_v1` | 9 | **2.8%** — worst |
| `safety_v1` | 7 | 2.2% |
| `instruction_following_v1` | 6 | 1.9% |
| `final_response_quality_v1` | 4 | 1.25% |
| `hallucination_v1` | **0** | **0%** |

So hardening this prompt can only recover tool use, not the other four — and the losses look
like general autorater flakiness (mostly different cases each pass) rather than a
prompt-specific JSON defect. `hallucination_v1` losing nothing across 320 scorings suggests
the ceiling is reachable.

## Cost, against the estimate

| | estimated | actual |
| --- | --- | --- |
| capture, 64 cases | — | **2.6 min** |
| one scoring pass, 5 metrics | — | **2.8 min** |
| whole campaign | 60–130 min | **~55 min of compute** |

The estimate assumed inference dominated and it does not — inference and scoring cost
almost the same. Nine scoring passes and five captures, no optimize stage, no agent
redeploy, and no `main` freeze.

## What to do with this

1. **Try more scoring passes before more `num_runs`.** For the holdout the judge is the floor,
   and averaging N scorings of one capture costs ~2.8 min each against ~2.6 min per inference
   pass *plus* engine risk. Campaign 03 should set this deliberately.
2. **Record which autorater scored a run**, and consider pinning the one we can. Nothing
   records it today, so a silent service-side model change would look like a result. Arm 3
   shows `tool_use_quality` can be pinned with a full resource name; the other four cannot.
3. **Do not re-derive the judge/agent split from n=5.** Repeat arm 1 at n ≥ 20 if the split
   itself matters; the per-case rates already answer the practical question.
